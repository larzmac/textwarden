# Larz's TextWarden Fork — Complete Documentation

A personal, fully-local replacement for a Grammarly subscription, built on
[PhilipSchmid/textwarden](https://github.com/PhilipSchmid/textwarden) (Apache 2.0).
Everything runs on this Mac: no cloud services, no accounts, no per-use cost.

Work lives on branch **`languagetool-engine`** (the fork's default branch).
Remote `upstream` points at the original project for periodic merges.

## What the fork adds, layer by layer

### 1. Grammar engine: LanguageTool with Harper fallback

Upstream checks grammar with [Harper](https://github.com/automattic/harper) (Rust,
compiled in). This fork adds a second engine — a local
[LanguageTool](https://languagetool.org/dev) server — for deeper rule coverage,
including statistical confused-word detection (*their/there*, *brakes/breaks*).

- `Sources/GrammarBridge/LanguageToolEngine.swift` — HTTP client for
  `POST /v2/check` on `localhost:8081`. Converts LanguageTool's UTF-16 offsets to
  the Unicode-scalar indices the app uses internally (emoji-safe — see the unit
  tests), maps LT rules onto TextWarden's category names so category filtering and
  "Ignore Rule" keep working, and declines texts over 20,000 chars (Harper handles
  those faster locally).
- `Sources/GrammarBridge/EngineRouter.swift` — routes each check:
  **Auto** (default) tries LanguageTool and silently falls back to Harper when the
  server is down (30 s failure cooldown so a downed server never adds latency);
  **LanguageTool** / **Harper** force one engine. Picker in Settings → General.
- The custom-vocabulary filter is applied client-side after either engine, so the
  personal dictionary works with both.

### 2. Latency hardening (for the HTTP engine)

Harper answers in ~10 ms; LanguageTool takes 50–300 ms. Three gaps that latency
exposed, all fixed in `Sources/App/AnalysisCoordinator*.swift`:

- **Stale-result protection** — a grammar generation counter plus a text-identity
  check; a result is dropped if a newer analysis started or the field's text
  changed while the check was in flight (otherwise underlines would land on the
  wrong words during fast typing).
- **Content-keyed result cache** — results are cached by text + dialect + engine
  and reused for identical text (upstream's cache was keyed by a per-keystroke
  UUID and never read).
- **Debounce floor** — 0.3 s (`TimingConstants.languageToolDebounce`) while a
  network engine is active; per-app debounces that are already longer still win.

### 3. Browser extension: TextWarden Web

`BrowserExtension/` — one Manifest V3 WebExtension for Safari and Chrome that
checks web text fields against the same local LanguageTool server:

- `background.js` proxies all server calls (Safari blocks `http://localhost`
  fetches from https pages inside content scripts; the background worker is
  exempt). 30 s offline cooldown, no console spam when the server is off.
- `content.js` tracks the focused `<textarea>`/contenteditable, debounces 600 ms,
  draws underline overlays via `Range.getClientRects()` (with block-aware text
  extraction so Gmail-style div-per-line editors get correct offsets), shows a
  count badge and a suggestion panel, and applies one-click fixes. Responses for
  since-edited text are dropped.
- `SafariExtension/TextWarden Web/` — Xcode wrapper app (bundle `io.textwarden.web`)
  generated by `safari-web-extension-converter`; Safari requires extensions to
  ship inside an app. Note: the app target's bundle ID must prefix the extension's
  (`io.textwarden.web` → `io.textwarden.web.Extension`) or the build fails.
- Known limit: Google Docs renders text to a canvas — no DOM, no extension
  support. Use the Mac app's hotkey flow there.

### 4. AI style engines: Apple Intelligence or local Ollama

Upstream's AI style suggestions / rewrites / sentence simplification run on
Apple's Foundation Models (on-device). This fork makes the backend switchable:

- `Sources/App/StyleEngine.swift` — a `StyleEngine` protocol mirroring
  `FoundationModelsEngine`'s API (analyzeStyle, regenerateStyleSuggestion,
  generateText, simplifySentence, generateReadabilityTips), a `StyleEngineMode`
  UserDefaults setting, and `StyleEngineFactory` which every call site now uses.
- `Sources/App/OllamaStyleEngine.swift` — the same five capabilities served by a
  local [Ollama](https://ollama.com) model via `POST /api/chat` with
  **structured outputs** (`format` = JSON schema), so responses parse into the
  same shapes as Foundation Models results and reuse the existing
  validation/diffing pipeline (`StyleTypes+Generable.swift`). Default model:
  `qwen3:30b-a3b-instruct-2507-q4_K_M` (fast mixture-of-experts; ~0.8 s per
  analysis warm on a Mac Studio). Model and server URL configurable.
- Picker in Settings → Style → "AI engine": **Apple Intelligence (built-in)** or
  **Ollama (local model)**. Both fully local.

### 5. Housekeeping

- Signing switched to the fork owner's team (`4S8278TRTP`); upstream's Sparkle
  auto-update feed removed so the fork can't "update" itself back to stock.
- `-framework OpenDirectory` added to linker flags (the Rust `sysinfo` crate
  needs it; upstream's pinned crates predate this).
- `console.json` — buttons for Larz's Project Console (rebuild/restart the app,
  manage the LanguageTool server, rebuild the Safari extension, run tests,
  start Ollama).

## Machine setup (what this Mac runs)

| Piece | Install | Runs as |
|---|---|---|
| TextWarden app | `xcodebuild -scheme TextWarden` (Rust auto-builds; needs rustup with both darwin targets) | Login item / manual |
| LanguageTool 6.8 | `brew install languagetool` | `brew services start languagetool` → localhost:8081, `--allow-origin` for the extension |
| n-gram data (14 GB) | `ngrams-en-20150817.zip` extracted to `/opt/homebrew/var/languagetool/ngrams/en`; enabled via `languageModel=` in `/opt/homebrew/etc/languagetool/server.properties` | loaded by the LT server |
| Ollama | Ollama.app (menu-bar) | localhost:11434 |
| Safari extension | build `SafariExtension/TextWarden Web`, launch the app once, enable in Safari Settings → Extensions | inside Safari |
| Chrome extension | `chrome://extensions` → Developer mode → Load unpacked → `BrowserExtension/` | inside Chrome |

First build quirk: a clean build fails once because swift-bridge generates
`GrammarEngineFFI.swift`/`SwiftBridgeCore.swift` mid-build — just build again.

## Verification

- Unit + integration tests:
  `xcodebuild test -scheme TextWarden -only-testing:TextWardenTests/LanguageToolEngineTests -only-testing:TextWardenTests/OllamaStyleEngineTests -destination 'platform=macOS'`
  (the Ollama live test skips when the server is off; offset tests cover emoji).
- LanguageTool sanity: `curl -d "text=I like to walk in the mourning." -d "language=en-US" localhost:8081/v2/check`
  should return `CONFUSION_RULE_MOURNING_MORNING` (proves n-grams are loaded).
- App smoke test: type "Ths is a testt. Their going to they're house." in
  TextEdit → underlines; `⌥⌃G` popover; accept a fix.

## Keeping up with upstream

```
git fetch upstream
git merge upstream/main
```

The fork's diff surface is deliberately small (mostly new files + one wiring
change in `Dependencies.swift` + factory calls at style call sites) to keep
merges cheap.
